# Mockey Redux 3.0.0-rc.2

This is the second release candidate of Mockey Redux 3.0.0. Mockey Redux is a mock server for HTTP services,
and a Kotlin rewrite of [Mockey](https://github.com/clafonta/Mockey). The candidate has everything that the
release is planned to have. Try it, and report what doesn't work in the [issues of the project][issues].

## What changed since the first candidate

One thing is new in this candidate:

- **A hint for a certificate that the Java runtime doesn't trust.** On a network that inspects TLS traffic,
  a proxy answers in place of every site, with certificates that a Java runtime doesn't trust by itself. A
  request that the server forwards to an `https` target then fails. The answer with the status 502 said
  that the certificate wasn't accepted, and it ended with the words of the Java runtime, which include
  `PKIX path building failed`. It didn't say what to do. Now it also says what the runtime needs: the root
  certificate of the issuer in its trust store. The same goes for a real service whose certificate comes
  from the certificate authority of a company. The new section
  ["The certificate of a real service"][certificate] of the server document shows how to add the
  certificate.

Nothing else is different in the two programs or in the library.

## What's in it

Mockey Redux does what Mockey 2.x did. It answers the requests for a service with a scenario, which is
chosen once or by what a request holds, or it forwards them to the real service. It has plans, twisting,
tags, request rules, request inspectors, and a history that replays a request and turns an answer into a
scenario. This is what's new:

- **Two programs.** `mockey-server` answers the mock requests, and `mockey-ui` serves the web pages that
  manage a server. The server works without the UI.
- **An admin API.** Whatever the pages do, a script or a test can do through a JSON API. The API describes
  itself in the OpenAPI format.
- **Definitions in files.** The server keeps its definitions as JSON files in a directory. A change
  rewrites only the files of what it changed, so the directory can live under version control. As before,
  the server starts in read-only mode, in which it writes nothing.
- **Fixed defects.** A mock URL with a variable, such as `customer/{id}`, matches the request for any
  customer again, and a response body is sent exactly as it's stored. The register at the end of these
  notes lists every such difference.
- **Safer defaults.** The admin API and the UI answer only programs on the same machine, unless they're
  told otherwise. An admin token protects the API where other machines reach it.
- **A library.** The mock engine, `mockey-core`, runs inside a JVM application or its tests, without an
  HTTP server.
- **A way over from Mockey 2.x.** The server imports the definitions of Mockey 2.x. With the legacy shim,
  it also answers the automation endpoints that the scripts for Mockey 2.x call.

## What it needs

A Java 21 runtime, and nothing else.

| File | What it is |
|---|---|
| `mockey-server-3.0.0-rc.2-runnable.jar` | The server as one file, which `java -jar` runs. |

## Getting started

The [quick start of the README][quick start] starts both programs from their runnable jars and defines a
first mock, in four commands. The documents of the project describe the rest: [the server][server],
[the UI][ui], and [the admin API][admin api].

Mockey is a tool for development and test networks. It has no user accounts and no TLS. By default, the
mock listener of the server accepts connections from other machines, and it forwards a request for an
absolute URL that no service knows to that URL. Read ["Security" in the server document][security] before
others can reach a server.

## Coming from Mockey 2.x

Mockey Redux isn't a drop-in replacement for Mockey 2.x. The [migration guide][migration] describes the
move step by step. These are the changes to plan for:

- The web pages have moved out of the server and into the program `mockey-ui`. The URLs of the old pages
  are gone.
- Administration has a listener of its own, which only programs on the same machine reach by default.
- The definitions have a new format. The server imports the definitions of Mockey 2.x from a definitions
  directory or from an export document.
- The automation endpoints `/config/service`, `/plan/setup`, `/definitions`, and `/home` answer only where
  the server is started with `--legacy-shim`.
- A request inspector that's a Java class of Mockey 2.x has to be ported to the interface of the new
  engine.
- There's no WAR file, and no single jar that holds everything. Each of the two programs comes as a
  distribution and as a runnable jar.
- The Image Depot, the page for mobile devices, the viewer of the debug log, and the loader of JSON Schema
  samples are gone.

## The deviation register

Mockey Redux fixes defects of Mockey 2.x, and each fix changes how the server behaves. The register lists
every intended difference in behavior between Mockey 2.x and Mockey Redux. A behavior that isn't listed
stays the same. So when a test suite that passed with Mockey 2.x fails with Mockey Redux, look for the
failure in the register first.

The last column says how the behavior of Mockey 2.x is known. An entry with **run** was observed in a
running Mockey 2.x, and it names the recordings or the probe of the repository that show it. An entry with
**read** was taken from the source code of Mockey 2.x.
